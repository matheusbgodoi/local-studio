# Production dependency qualification — 2026-09-07

## Scope and evidence

MEASURED / PROVEN: `npm audit --omit=dev --json` for the frontend reported 12 vulnerable package nodes (7 high, 5 moderate). This is distinct from an installation summary that also includes development dependencies. The updated frontend production graph reports 3 nodes (2 high, 1 moderate). The standalone agent runtime's `bun audit --json` returns an empty object. The controller's full Bun audit still reports development dependencies; traversal from its production dependencies found none of those audited packages in the production graph.

The audit identifies vulnerable installed versions, not demonstrated exploitation of this application. No exploit payload was sent to a live service. Dependencies were installed in an isolated worktree; the installed Mac application and remote inference host were unchanged.

## Reachability assessment

The [Mermaid security patch](https://github.com/mermaid-js/mermaid/releases/tag/mermaid@11.16.1) addresses diagram-based injection and denial of service. This is directly relevant to `frontend/src/features/agent/ui/filesystem-preview.tsx`, which renders Mermaid blocks from opened files. DOMPurify's [3.4.13 patch](https://github.com/cure53/DOMPurify/releases/tag/3.4.13) covers a specific in-place hook issue; this repository does not configure that hook, so exploitation through the application was not established.

The [Hono 4.12.34 security release](https://github.com/honojs/hono/releases/tag/v4.12.34) fixes CORS parsing, JSX memoization, language middleware and proxy-helper issues. The controller uses CORS with explicit allowed headers, which avoids the documented default-header trigger. No application use of the affected JSX memo, language middleware or proxy helper was found. The patch still removes vulnerable implementations from the dependency graph.

The [Undici advisory](https://github.com/nodejs/undici/security/advisories/GHSA-4cwx-7wf7-3272) requires its cache interceptor for the reported shared-cache disclosure and parser failure. Source tracing found Client/Pool/EnvHttpProxyAgent usage, not cache or retry interceptors. This lowers demonstrated reachability; it does not make the vulnerable version fixed. Runtime 8.9.0 closes the listed advisories without changing dispatcher major versions.

The [fast-uri advisory](https://github.com/fastify/fast-uri/security/advisories/GHSA-f65p-4m7j-42xc) and [ip-address advisory](https://github.com/beaugunderson/ip-address/security/advisories/GHSA-mwp4-54f8-5fhr) describe malformed-host interpretation risks. Here their observed dependency paths are schema handling and rate limiting; this audit did not establish that application outbound-host authorization uses either vulnerable function. TOML is pulled by Effect, with no direct application TOML configuration parser found. Nanoid's affected custom-generator behavior was not found in application code. These are dependency findings, not claimed remotely exploitable product defects.

## Remaining frontend limitation

MEASURED / PROVEN: Pi 0.83.0 publishes `npm-shrinkwrap.json`. Its frontend npm installation retains Undici 8.5.0 and brace-expansion 5.0.7 despite scoped overrides and targeted npm update attempts. The two vulnerable nodes plus Pi's inherited advisory remain in the production audit. The [brace-expansion advisory](https://github.com/advisories/GHSA-rgw5-rvv9-x895) concerns resource exhaustion during expansion; Pi uses glob/minimatch, so untrusted agent patterns are a relevant input boundary. No denial-of-service reproduction was attempted.

Bun resolves the standalone runtime differently and applies its existing brace-expansion 5.0.9 override and new Undici 8.9.0 override. Therefore a clean runtime audit must not be presented as a clean frontend or packaged-app audit. Resolving the frontend shrinkwrap requires separate Pi upgrade or upstream packaging qualification. This milestone deliberately does not replace the owner's Pi pin, rewrite a published shrinkwrap, or claim all dependency findings are closed.

## Actual package closure inspection

MEASURED / PROVEN: inspection of the installed application, including `app.asar`, found the following physical copies. Node's ESM resolver was used without executing Pi to identify its Undici and minimatch → brace-expansion resolution.

| Physical tree | Undici | brace-expansion | Evidence |
| --- | --- | --- | --- |
| Installed `Resources/app/agent-runtime` | 8.5.0 | 5.0.9 | Normal runtime Pi dependency resolution |
| Installed Next standalone, nested under Pi | 8.5.0 | 5.0.7 | Both files ship and resolve from that Pi package |
| Installed `app.asar` | 8.5.0 | 5.0.9 | Archive package inventory; normal chat use not established |
| Qualified isolated portable runtime bundle | 8.9.0 | 5.0.9 | Actual bundle built successfully, 124 copied packages; Pi resolution confirmed |

The frontend copy is not merely an unshipped development dependency. `complete-standalone` explicitly copies its entire Pi package tree; `afterPack` requires that CLI to exist. `resolvePackagedPiCli` in `litter-bridge-gateway.ts` selects it as a fallback when ordinary runtime Pi import resolution fails. No direct Pi import was found in the installed Next server JavaScript chunks. Therefore the vulnerable nested copy is a shipped fallback path, while the upgraded standalone runtime is the normal target path. This inspection does not demonstrate exploitation or routine execution of the fallback.

The root checkout's previously compiled Next tree also retained the nested vulnerable versions. Its runtime `dist` contained the TypeScript build output rather than the portable bundle at inspection time: the final runtime check can replace the portable output made earlier in the frontend build. Final desktop packaging must use the normal desktop build flow, which regenerates the portable runtime, and inspect the resulting candidate again. The isolated qualification did not modify the root build output or the installed application.


## DECIDED / APPLIED — one packaged Pi closure

The packaging follow-up supersedes the earlier shipped-fallback limitation. The frontend npm audit still reports the pinned development/build dependency tree, but that vulnerable Pi tree is no longer shipped in the qualified candidate. Pi remains 0.83.0.

- Next no longer forces Pi providers into every API trace or copies the entire frontend Pi shrinkwrap tree into standalone output. The existing standalone guard rejects a duplicated Pi tree.
- The packaged fallback CLI resolves under `Resources/app/agent-runtime/node_modules`, using the same portable Pi closure as normal agent execution. Packaging still checks that the CLI and its runtime entrypoints exist.
- Electron ASAR excludes Pi packages, Undici and brace-expansion. Static inspection of compiled desktop imports found Electron, effect, electron-updater, node-pty and qrcode. Their production/optional dependency traversal covered 63 package nodes, with none of the excluded packages. This is targeted removal of unused copies, not a blanket removal of ASAR dependencies.

MEASURED / PROVEN: an unsigned macOS candidate was built in the isolated worktree using the existing Next build, desktop TypeScript/helper build, and electron-builder directory packaging. Its actual ASAR and Next standalone contain no Pi, Undici or brace-expansion copies. Its dedicated runtime contains exactly Pi 0.83.0, Undici 8.9.0 and brace-expansion 5.0.9. The candidate's bundled Electron Helper executed that exact Pi CLI with `--help` successfully, producing usage/provider options and exit status 0 without inference. The package passed its normal afterPack checks.

The existing Swift helper emitted sendability warnings but built successfully. No candidate was installed or launched as the user's application; full installed chat/tools/restart acceptance remains root integration work.
